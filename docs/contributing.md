# Contributing

## Development setup

Clone the repository and install with the dev dependency group:

```bash
git clone https://github.com/bmds-tue/nf-meta
cd nf-meta
uv sync --group dev
```

### Editor in dev mode

The browser editor's frontend lives under `src/nf_meta/editor/frontend`. During development it
runs as a separate Vite dev server with hot reload:

```bash
cd src/nf_meta/editor/frontend
npm install
npm run dev          # serves on http://127.0.0.1:5180
```

With the frontend dev server running, start the editor with `NF_META_DEVMODE=1`, so the backend
serves the API for the dev server instead of the bundled build:

```bash
NF_META_DEVMODE=1 uv run nf-meta editor [path/to/metapipeline.yaml]
```

In a dev container, add `--no-redirect-file` so VS Code can open the link in your browser.

Open the link it prints (`http://127.0.0.1:5180/?token=…`): the API needs the session token it
carries; a plain <http://127.0.0.1:5180/> shows an access notice. In dev mode the API always runs on `127.0.0.1:8080` (the dev
server proxies `/api` there) and `--host` / `--port` are ignored. nf-meta exits with a hint if the
dev server isn't running.

Frontend checks:

```bash
cd src/nf_meta/editor/frontend
npm test             # unit tests (Vitest)
npm run build        # type-check and build into ../frontend_dist
```

## Tests and type checking

```bash
uv run pytest
uv run mypy src/nf_meta
```

Tests that run real Nextflow are marked `nextflow` and deselected by default. They need Java 17+
and Nextflow on `PATH` (the devcontainer installs both) and skip themselves otherwise:

```bash
uv run pytest -m nextflow
```

They pin down Nextflow behavior the runner relies on (resume sessions, launch-dir-relative
paths); see `tests/integration/test_nextflow_assumptions.py`. CI runs them in a separate job.

## Documentation

Docs sources live in `docs/` on `main`, built with [MkDocs](https://www.mkdocs.org/) (using the [material theme](https://github.com/squidfunk/mkdocs-material)) and
[mike](https://github.com/jimporter/mike) for versioning.

```bash
uv sync --group docs
uv run mkdocs serve
```

The **`gh-pages` branch is auto-generated by a workflow** running `mike`.
The workflow creates and updates it and it shares no history with the `main` branch. 
It must not be edited it by hand.

### Editor screenshots

The main editor screenshot (dark and light, in `docs/editor/`) is taken from
`assets/metapipeline.yaml` by a script. The docs workflow runs it for every release, and the
README shows the images from the published docs:

```bash
uv run --with playwright playwright install chromium   # once
uv run --with playwright python scripts/editor_screenshots.py
```

### Deploying

- [ ] Normal release → leave "Set as the latest release" **ticked**.
- [ ] Backport release (publishing an older series) → **untick** it, or
      `latest` wrongly moves to the older series. To repair after the fact:
      open the release you actually want as latest and re-tick it there —
      that re-fires the workflow for the right series and fixes the alias.
      Unticking the wrong one does *not* move `latest` back by itself.
- [ ] If a push to `main` and a release land close together, the second
      workflow run queues rather than racing (`concurrency: docs-publish`,
      `cancel-in-progress: false`) — a delay there is expected, not a failure.
- [ ] A tag/release older than when `mkdocs.yml` was added will show the `docs`
      workflow run as skipped with a `::notice::`, not failed red — expected.

### If a deploy goes wrong

- [ ] Check the run actually fetched `gh-pages` before calling `mike`
      (`git fetch origin gh-pages:gh-pages` step). If this step is ever
      missing or edited out, `mike` sees no prior versions and republishes a
      tree containing *only* the version it just built, wiping every other
      published version.
- [ ] Site root (`https://bmds-tue.github.io/nf-meta/`) returns 404 while
      `/latest/` works → `gh-pages` has no root `index.html`. It is written by
      the "Point site root at latest" step, which only runs on the release
      holding the `latest` alias; re-run the `docs` workflow manually with that
      release's tag to restore it.
- [ ] Pages serves with `max-age=600`, so a fresh deploy can take up to ~10
      minutes to show in a browser — hard-refresh before assuming it failed.
- [ ] Check the released version didn't get the dev banner — `NF_META_DOCS_IS_DEV`
      should read `false` in that run's "Publish" step logs whenever a tag is
      present.
